# Stat engine and Affixes redesign — design

**Date:** 2026-10-11
**Branch:** `stat-engine`
**Status:** design approved section by section in brainstorming (2026-10-11); awaiting the user's review of this file

## Intent

Describe item properties the way the game does, from the game's own tables, instead of copying upstream's
pre-written English. The first users are the Affixes tab and the Item Builder; a stat-summing spec (the Item
Builder's full item tooltip) follows and reuses the same engine.

Two problems motivate it:

- **Upstream's display text has bugs.** Its generator resolves duplicate string keys by file order, so the Paladin
  skill tab prints "+# to Summoning Skills (Paladin Only)" where the game prints "Combat Skills". It prints
  "Level -5 Telekinesis (-20 Charges)" for charges whose level and count scale with item level. And its item-type
  names are lossy ("Staff Class" for an orb-only exclusion; see the Item Builder spec's "Data findings").
- **Text can't be filtered by stat.** Finding every affix that gives Cold Resist means knowing that *All
  Resistances* also does. Today a text workaround (`MOD_EXPANSIONS`) appends implied words to the search text.

### Success criteria

- Every affix row's lines are produced by the engine from `Properties.txt`, `ItemStatCost.txt` and the game's string
  tables, with no English parsed anywhere.
- The engine follows the game where the sources settle it (D2MOO, the vanilla tables, in-game tests) and every rule
  that isn't settled is named below.
- The Affixes tab gains a Stat filter that finds direct and indirect sources of one stat.
- `Affixes.json` is generated by the fork, so it always matches the game tables it was built from.
- Every tab except Affixes and Item Builder is pixel-identical before and after.

### Out of scope (this spec)

- **Stat summing** (the builder's full item tooltip, base lines such as Defense, damage and requirements, and
  cross-affix merges): the next spec. Its research is already in the vault (see "Research").
- Rendering uniques, runewords, sets, sacreds or corruptions through the engine. `UniqueItems.txt` already has the
  same `prop/par/min/max` shape, so a later spec can.
- A stat filter in the builder; choosing several stats at once.
- Item-type filtering by base or chain (the "item-type view" idea was declined).
- `package.json` version and `Changelog.json`, as before.

## Research

Evidence lives in a local vault, `docs/research/stat-summing/` (ignored through `.git/info/exclude`, never committed;
start at its `INDEX.md`): the mod-repo tables, the decoded string tables, analysis scripts, `notes/data-findings.md`,
`notes/web-research-report.md` (how the game and community tools sum and describe stats) and
`notes/base-lines-report.md` (for the summing spec).

### How the game describes properties

- **Property → stats.** Each affix mod `{code, param, min, max}` names a `Properties.txt` row, whose `func1–7` /
  `stat1–7` turn it into stats. Values are summed per (stat, layer) (D2MOO `ITEMMODS_AddPropertyToItemStatList` →
  `STATLIST_AddStat`).
- **Stats → lines.** `ItemStatCost.txt` gives each stat `descpriority`, `descfunc`, `descval` and string keys
  (`descstrpos`, `descstrneg`, `descstr2`), plus a `dgrp` group whose members print as one line only when all are
  present and equal ("All Resistances"). The damage pairs (min/max per element, cold and poison length, ED%) are
  hardcoded in the game, not in the tables.
- **Strings** come from three tables, looked up patch → expansion → base: SoE's `patchstring.tbl` (in the mod repo)
  and the base game's `string.tbl` and `expansionstring.tbl` (only in Blizzard's MPQs). The `.tbl` format is a fixed
  binary layout: a 21-byte header, a `u16` index array, then 17-byte hash nodes.

### Measured on SoE's data

- **Coverage is complete.** All 1,412 affix rows (map affixes included) reach stats that have `ItemStatCost` rows;
  all 299 `ItemStatCost` string keys resolve (207 from SoE's patch table, 8 expansion, 84 base); all 35 `CharStats`
  class and skill-tab keys resolve (30 patch, 5 base).
- **Property funcs used:** 1, 2, 3, 5, 6, 7, 8, 10, 11, 14, 15, 16, 17, 19, 20, 21. **`descfunc`s used:** 1, 2, 3, 4,
  6, 7, 8, 9, 11, 13, 14, 15, 20, 24. Stats with no `descfunc` (`coldlength`, `poisonlength`, `item_numsockets`,
  `item_skillonhit`, `item_skilloncast`) print only through a pairing or a special case.
- **Duplicate string keys** exist in every table (6 with differing values in SoE's patch table). The game resolves a
  key by hash probing, starting at the stored hash modulo the table size, first match wins; file order gives wrong
  answers. In SoE: `StrSklTabItem6` → "+%d to Combat Skills"; `strModEnhancedDamage` → "Enhanced Damage\n".
- **Unknown codes.** `Deep-Wounds` (capital D; 5 suffixes and some uniques) isn't in `Properties.txt`, which has
  `deep-wounds`. **In-game test (the user, `Diablo II.exe -direct -txt`, a `CubeMain.txt` recipe with output
  `usetype,rar,suf=806`):** the item shows "Open Wounds Damage Per Second", so the game matches property codes
  case-insensitively. No two `Properties.txt` codes differ only by case. `map-mon-droparmor` and
  `map-mon-dropweapons` match nothing; upstream shows no text for their 12 rows (*of the Smith*, *of the Armorer*).
- **Multi-line strings.** **In-game test (the user):** a string with `\n` stacks bottom-up.
- **Priority ties.** Only one pair of displayed stats on one affix shares a `descpriority`: the map affixes' Magic
  Find and Gold Find (126 rows). The game breaks ties with qsort.
- **Charges with negative values** (D2MOO `ITEMMODS_PropertyFunc19`): a negative `max` makes the skill level
  `⌊(ilvl − reqlevel) / max(1, ⌊max(1, 99 − reqlevel) / −max⌋)⌋`, at least 1; `max = 0` makes it
  `⌊(ilvl − reqlevel) / 4⌋ + 1`, clamped to 1…`maxlvl` (20 when `maxlvl` ≤ 0). A negative `min` makes the charges
  `⌊level · −min / 8⌋ − min`; the result (or a positive `min`) is clamped to 1–255, and 0 means 5. `reqlevel` and
  `maxlvl` are `Skills.txt` columns.
- **Damnation:** its compiled `itemstatcost.bin`, `properties.bin` and `charstats.bin` are byte-identical to
  Standard's, and its `patchstring.tbl` differs in two item-description keys the engine never uses. The engine
  ignores the Damnation toggle, like the builder.
- **Item-type names.** Upstream's names are mostly `ItemTypes.txt`'s `ItemType` column, but weapon classes use the
  tooltip strings (`WeaponDescStaff` = "Staff Class" covers `orb`, `staf` and `wand`).

## Decisions

| Question | Decision |
|---|---|
| Faithful formatter, display-string templates, or a code alias table? | The game's way: `Properties.txt` funcs, `ItemStatCost.txt` descfuncs, the string tables. No English parsing. |
| Language for the decoder and engine | JavaScript, as Node-safe modules run by a Vite plugin (the `drop-calc-data` / `item-builder-data` pattern). No Python, Rust or C toolchain. |
| When does the engine run? | **At build time only**, in this spec. The plugin writes each row's lines and stat keys; the browser only displays. The summing spec will ship the engine's dictionary to the browser. |
| Where do strings come from? | SoE's `patchstring.tbl` committed raw (it's public in the mod repo). Base and expansion strings committed only as `src/baseStrings.json`: every key the committed tables reference, extracted from the user's own MPQ files. Blizzard's full tables are never committed. |
| Upstream's `Affixes.json` | Deleted from the fork; the plugin generates `public/data/standard/Affixes.json` (gitignored). An upstream merge that touches it is resolved by keeping it deleted. |
| Where do the tables live? | In their in-MPQ paths: `public/data/<mode>/data/global/excel/*.txt` and `public/data/standard/data/local/LNG/ENG/patchstring.tbl`, so a later build step could extract them from MPQs unchanged. Every existing table moves too. |
| Builder text | The engine's lines everywhere in the builder (slots, list rows, search). |
| Per-level wording | "+0-74 to Mana (Based on Character Level), 0.75 per level" |
| Stat filter | One stat at a time; indirect sources stay in the list, tagged "via …". |

## Design

### File layout

```
public/data/standard/data/global/excel/      MagicPrefix, MagicSuffix, ItemTypes, Weapons, Armor, Misc,
                                             MonStats, TreasureClassEx, Levels, ItemRatio, UniqueItems, SetItems
                                             (moved), Properties, ItemStatCost, CharStats, Skills, Skilldesc (new)
public/data/standard/data/local/LNG/ENG/     patchstring.tbl (new)
public/data/damnation/data/global/excel/     the Damnation tables (moved)
public/data/standard/                        DropCalculator.json, ItemBuilder.json, Affixes.json (generated)
public/data/damnation/                       DropCalculator.json (generated), Uniques.json (upstream)
src/baseStrings.json                         trimmed base/expansion strings (committed, generated by a tool)
```

File names keep the mod repo's spelling (`Skilldesc.txt`). The JSON files the app fetches stay where they are.

### Modules and data flow

```
excel/*.txt + patchstring.tbl + src/baseStrings.json
        │  affix-data plugin (vite.config.js)
        ├─ src/tblFile.js      decode .tbl, hash-probe lookup
        ├─ src/statData.js     tables → stat dictionary, loud checks
        ├─ src/statEngine.js   mods → stat entries → lines, stat keys
        └─ src/affixData.js    raw affix rows → generated rows
        ▼
public/data/standard/Affixes.json      → Affixes tab (src/affixesLoad.js)
public/data/standard/ItemBuilder.json  → Item Builder (unchanged loading)
```

| Module | Role | Tests |
|---|---|---|
| `src/tblFile.js` | `parseTbl(bytes)` → `Map` of key → string, duplicates resolved by the game's hash probe; header sanity check. | `tblFile.test.js` |
| `src/statData.js` | Builds the stat dictionary: `Properties.txt` rows by lower-cased code, `ItemStatCost.txt` rows by stat with strings resolved (patch, then `baseStrings.json`), `CharStats.txt` class strings, skill names (`Skills.txt` → `Skilldesc.txt` `str name` → string), each skill's `reqlevel` and `maxlvl`. Runs the loud checks. | `statData.test.js` |
| `src/statEngine.js` | `expandMods(mods, dict, ctx)` → stat entries; `describe(entries, dict)` → lines; `statKeysOf(mods, dict)` → filter keys; `statOptionLabel(key, dict)`. Pure. | `statEngine.test.js` |
| `src/affixData.js` | Raw `MagicPrefix`/`MagicSuffix` rows → generated Affixes rows and the stat options; replaces the builder's `joinAffixes`. | `affixData.test.js` |
| `src/affixesLoad.js` | Fetch `Affixes.json` once, cache, retry after a failure (like `itemBuilderLoad.js`). | — |
| `tools/extract-base-strings.mjs` | `node extract-base-strings.mjs <string.tbl> <expansionstring.tbl>` → `src/baseStrings.json`. Run by someone with the game files; not part of the build. | — |

`src/itemBuilderData.js` keeps bases, item types and the builder's format, and takes its affix rows from
`affixData.js`.

### The plugin

`item-builder-data` becomes **`affix-data`**. It writes `Affixes.json` and `ItemBuilder.json` from the same rows,
with the existing timing: at startup in dev and build, again in dev when a source file changes (the `excel/` tables it
reads, `patchstring.tbl`, `src/baseStrings.json`, `Weapons.json`, `Armors.json`), skipped under Vitest and
`vite preview`, writing only when the content changed. The link-version fingerprint (affix key, side, name, level,
group; base codes) is unchanged. `ItemBuilder.json`'s format `version` becomes 2.

`drop-calc-data` reads from the new `excel/` folders; nothing else about it changes.

### The engine

**Expansion: mods → stat entries `{stat, layer, min, max}`**, following `Properties.txt` as D2MOO does:

- The code is looked up case-insensitively. An unknown code yields no entries and a build warning.
- Funcs 1, 2, 8 and 13 take min..max. Func 3 reuses the previous slot's value (`res-all`). Funcs 15, 16 and 17 take
  min, max or param; for the `*/lvl` codes the value is the param, in eighths per character level. Func 7 writes
  `item_mindamage_percent` and `item_maxdamage_percent` together. Funcs 5 and 6 write min and max damage (which
  weapon stat they hit only matters for base lines, in the summing spec). Funcs 10 and 21 take the layer from the
  param or the `val` column. Func 11: chance = min, skill level = max, skill = param. Func 14: sockets. Func 19:
  charges, by the rule in "Research". Func 20: the indestructible flag.
- **Context:** `ctx = {ilvl}` or nothing. Without an ilvl (the Affixes tab, and the builder in this spec), values that
  depend on it (charges) become ranges over ilvl from the affix's `level` to 99.

**Description: entries → lines**

1. **Sum** per (stat, layer).
2. **Pairs:** min and max damage per element (fire, lightning, magic, cold with length, poison with length, poison
   shown as total damage over seconds), plain min and max damage, and ED% (min% equal to max%) each print one line.
3. **`dgrp`:** a group prints one line (with `dgrpfunc`, `dgrpval`, `dgrpstrpos`) when every member is present with an
   equal range; otherwise each member prints its own line.
4. **Formatting** by `descfunc` and `descval` with the resolved strings. A single value prints as-is; a range prints
   `a-b`, or `-a to -b` when negative. In a string with two or more values, each range is bracketed:
   "Adds [20-30]-[64-101] cold damage". The game's own wording and case are kept.
5. **Per-level stats:** the range over character levels 1–99, then the rate: "+0-74 to Mana (Based on Character
   Level), 0.75 per level".
6. **Order:** `descpriority`, highest first, 0 last; ties keep `ItemStatCost.txt` row order.
7. **Strings:** `ÿc` colour codes are stripped. A string containing `\n` is split, empty pieces are dropped, and the
   pieces print in reverse (the last piece is the top line).

### Generated `Affixes.json`

```js
{
  version: 1,
  stats: [{key: "coldresist", label: "Cold Resist +#%", group: "Items"}, ...],
  affixes: [{
    key: "p352", suffix: false, name: "Lapis", level: 35, maxLevel: null, requiredLevel: 26,
    rare: true, frequency: 3, group: 117,
    classSpecific: null, className: null,
    itemTypes: ["Weapon", "Armor", "Helm", "Boots"], excludedItemTypes: ["Orb"],
    lines: ["Cold Resist +11-20%"],
    statKeys: [{key: "coldresist"}],
    sort: {property: "res-cold", max: 20},
  }, ...]
}
```

(Values are illustrative.)

- **Rows:** the raw rows with `spawnable = 1` and `frequency > 0`, prefixes then suffixes, in file order. `key` is the
  builder's affix key (`p<row>` / `s<row>`).
- **`itemTypes` / `excludedItemTypes`:** `ItemTypes.txt`'s `ItemType` name for each `itype` / `etype` code, so names
  are exact. A code missing from `ItemTypes.txt` is skipped with a warning (one live row uses the item code `amu`).
- **`className`:** the class's full name ("Sorceress").
- **`sort`:** the source code and max of the first printed line; the Attributes sort reads it.
- **`ItemBuilder.json` affixes** carry the same `lines` and `sort` in place of `displayProperties`.

### Affixes tab

- **Loading:** `src/affixesLoad.js` fetches `data/standard/Affixes.json`; same loading and error states as today.
  `useJson` (which expects an array) is no longer used for this tab.
- **Columns:** Attributes renders `lines`; Item types and Excluded render the exact names; Class renders `className`.
- **Item type filter:** its options are the exact names (Staff, Orb and Wand instead of "Staff Class").
- **Sort:** `sortCompare.js` reads the new fields (`itemTypes`, `excludedItemTypes`, `className`); `attrs` reads `sort`
  and keeps today's behaviour (cluster by property, largest max first within a cluster).
- **Search:** the name plus `lines`. `MOD_EXPANSIONS` stays for this tab and the others.
- The tab's text and type names change by design; its layout, the multi-sort and the floating header don't.

### Item Builder

- Slots, list rows and search use `lines`; "Attributes ▼" uses `sort`.
- Charged skills show their ilvl range, as on the Affixes tab. Exact values at the builder's ilvl come with the
  summing spec's runtime engine.
- Nothing else changes (rules, odds, URL format, link version).

### The Stat filter

- **Entries:** one per line the engine can print. A plain stat is one entry (`coldresist`); a layered stat is one per
  layer ("+# to Fire Skills (Sorceress Only)", "#% Chance to cast level # Nova on striking"); a damage pair is one
  entry; a `dgrp` line is its own entry ("All Resistances +#%") and matches only rows that print that line. Stats
  with no `descfunc` get no entry.
- **Labels:** the engine's own line with `#` for each value, so a label always matches the rows' text.
- **Matching:** a row matches directly when it prints the line. It matches **indirectly** when it reaches the stat but
  the line folded into a group line; its `statKeys` entry then carries `via` (the group line's label without the
  value, e.g. "All Resistances"). The plugin computes it all; the browser compares keys.
- **Options:** the `stats` list, holding only stats some row reaches, under two `SearchableSelect` headings: **Items**,
  and **Maps** (stats reached only through `map-*` codes). Alphabetical within each.
- **UI:** a "Stat" `SearchableSelect` in the Affixes Filters bar after Prefix/Suffix, empty value "Any stat". It
  combines with search, item type and Prefix/Suffix by AND. It lives in `App` state like the other filters, isn't in
  the URL, and changing it returns to page 1 and row 0 (the existing filter-signature rule). While a stat is chosen,
  an indirect row shows "via All Resistances" in small text under its lines.
- **Mobile:** the select joins the Filters bar's mobile layout; the rules are duplicated across the 980, 720 and 480px
  blocks in `styles.css`, so all three are checked.

### Errors

**Loud checks** (the build fails; dev logs and keeps running):

- a required column is missing from any table;
- a reachable stat's string key resolves in neither `patchstring.tbl` nor `baseStrings.json`;
- a reachable stat uses a `descfunc`, or a mod uses a property func, that the engine doesn't implement;
- a skill param isn't in `Skills.txt`, or its name string is missing;
- a `.tbl` header disagrees with the file's size.

**Warnings only:** an unknown property code (it yields no line); an item-type code missing from `ItemTypes.txt`.

**`tools/extract-base-strings.mjs`** writes every key the committed tables reference that exists in the base or
expansion table, even where the patch table overrides it today, so a future SoE patch that drops a key still builds.
It needs re-running only when a data update makes the string check fail.

## Testing and verification

### Unit tests (Vitest, beside each module)

- **`tblFile.test.js`:** a `.tbl` built in the test, including duplicate keys whose hash-probe winner differs from
  file order; the header check; real-file smoke tests on SoE's `patchstring.tbl` (`StrSklTabItem6` → "+%d to Combat
  Skills", `strModEnhancedDamage` keeps its `\n`).
- **`statData.test.js`:** each loud check fires on a fixture; `Deep-Wounds` finds `deep-wounds`; skill names resolve.
- **`statEngine.test.js`:** hand-computed cases for every property func and `descfunc` in use; pairs; `dgrp` with equal
  and unequal ranges; range and negative formatting; bracketing in two-value strings; per-level wording; the charges
  rule at a fixed ilvl and as a range; `\n` bottom-up splitting; colour-code stripping; order and ties.
- **`affixData.test.js`:** the file format; `statKeys` with `via`; options under Items and Maps; exact type names
  (*Lapis* `p352` excludes "Orb").
- **Real data:** a golden snapshot of every row's lines (`src/__snapshots__/affixLines.golden.txt`), accepted after
  reviewing the upstream diff report below; spot checks on *Shimmering* ("All Resistances +3-6%"), the Paladin skill
  tab ("Combat Skills"), *of Bleeding* (an Open Wounds damage line) and the *of the Smith* rows (no lines).
- **Updated:** `sortCompare.test.js` (new fields), `itemBuilderData.test.js` (the row-join tests go).

### Review aid

`tools/checks/diff-affix-lines.mjs` compares each row's `lines` with upstream's last `Affixes.json` (read from git
history) and writes a Markdown report into the research vault. Each differing row gets one verdict: upstream bug or
engine bug. It isn't a gate and its output isn't committed.

### Browser checks

- **New `tools/checks/check-affix-stats.mjs`**, desktop then 390×844: choose Cold Resist and see direct rows plus
  "via All Resistances" rows; combine it with Prefix/Suffix; the Item type options are exact names; no horizontal
  overflow.
- **Still passing:** `check-itembuilder.mjs` (updated for the new text), `check-multisort.mjs`, `check-sticky.mjs`,
  `check-select-keyboard.mjs`, `check-dropcalc.mjs`.

### In-game checks (the user, `-direct -txt` plus a `CubeMain.txt` recipe)

- A *Teleportation* suffix at a known ilvl: the skill level and charges match the D2MOO rule.
- A map with the Magic Find and Gold Find suffix: the line order matches `ItemStatCost.txt` row order.

### Regression gates

- **The table move is its own first commit:** only paths change, and the Drop calculator's golden snapshot stays
  identical.
- `compare-desktop.mjs` before and after, diffed with `diff-shots.mjs`: every tab identical except Affixes and Item
  Builder.
- `npm run lint` at 0 problems; `npm test` green; `npm run build` succeeds.
